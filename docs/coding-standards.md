# 代码与变更规范

本规范约束手写生产代码、测试和工具脚本。层次关系见[架构](architecture.md)，UI 特有约定见[界面开发](ui-development.md)，并发与持久化见[生命周期](data-lifecycle.md)。

## 文件与包

1. 先查调用点、同类实现和真实所有者，再决定放置位置。文件名表达职责，如 `playlist_cache.go`，不使用难以辨认的临时名称。
2. 简单功能可以平放；只有多文件功能、独立依赖或复用能力才建子包。禁止仅为镜像目录而添加空层级。
3. 不创建无边界的 `utils`、`common`、`manager` 大包。工具函数留在使用者附近，共享时按具体能力命名。
4. 平台差异放入 `_darwin.go`、`_windows.go`、`_linux.go` 或有明确构建约束的文件；提供必要的其他平台实现。
5. 生产代码不导入测试工具。测试夹具不进入运行时 API，已有特殊测试接入口应复用，不继续扩大。
6. 删除行为时同步检查状态、回调、平台实现、测试、资源、配置和文档；共享能力有其他调用者时保留。

## 文件头与注释

每个代码文件头部都应有简短职责简介，测试文件也一样。Go 使用多行块注释；Python 使用模块文档字符串；Shell 使用连续 `#` 行。

```go
/*
管理歌单快照的发布与缓存裁剪，协调账号切换后旧结果的失效。
*/

package library
```

简介说明“做什么、归谁管”，不逐项列出所有函数，不写“本文件包含一些工具方法”。通常一至两句足够；复杂算法的解释靠近实现。

- 构建标签保留在最前面，标签组后空行，再写简介；不能吞进块注释。
- 保留版权、许可证和 `Code generated ... DO NOT EDIT.` 标记。
- 生成文件的简介同步到生成器，不只改生成结果。例如 [scripts/sherpa/main.go](../scripts/sherpa/main.go)与 [natives.go](../internal/features/speech/natives.go)。
- Python/Shell 保留 shebang 和编码声明位置。若帮助脚本按行提取注释，修改文件头时必须检查帮助输出。
- 原有包说明、导出 API 注释和必要的内存布局解释继续保留。文件简介不替代函数契约。
- 新测试前用一句注释写可观察行为；回归测试说明原先错误发生的条件。

注释优先解释所有权、请求时序、平台约束和算法理由。不要写任务过程、个人姓名、虚构性能收益或每次修改日期。

## 格式、命名与 API

只对本次涉及的 Go 文件运行 `gofmt -w`，检查未涉及文件没有顺手改格式。导入沿用标准库、外部依赖、内部包的分组；标识符采用 Go 惯例，如 `ID`、`URL`、`UI`。

函数名描述行为；布尔变量表达明确状态。导出标识符只为实际跨包需要开放。优先使用值类型表达有限、稳定的配置，避免为了几个选项引入任意字符串键和多级 map。

不要在不同层创建同义类型后反复转换。API 需要小接口时由消费者需求决定；不为一个实现建立 Repository/Service/Facade 的重复封装。避免只有换名作用的转发函数。

常量应承载共享语义或易错参数，不为了消除每个字面量而拆散可读代码。配置默认值集中在 `preferences.Default`，选项文案和界面格式化归视图。

## 错误与失败

- 保留错误来源，用 `fmt.Errorf("操作上下文: %w", err)` 支持 `errors.Is/As`，不要为判定错误解析用户提示文本。
- 区分永久限制、暂时网络失败、取消、未找到、无权限和存储不可用；沿用已有恢复策略。
- 失败不可伪装成成功的空列表、纯音乐、播放自然结束或账号退出。
- 能保留旧可用数据时保留；乐观更新失败只回滚自己的修改，不能覆盖用户的新操作。
- 日志提供动作与范围，不输出 Cookie、令牌、完整账号数据或私有歌词样本。
- 不通过 `recover`、忽略返回值或不断重试掩盖所有权错误。确实允许忽略时说明理由，如尽力清理已经不存在的临时文件。

## 输入与副作用

从 UI 传入的值需要明确校验边界。配置中的存储路径不应被反序列化覆盖内部写入路径；导出文件名需规范化，格式按实际字节识别。不要把未验证输入拼成 shell 命令。

副作用放在明确命令或事件中，禁止在每次渲染中重新发请求、写设置、创建窗口或注册快捷键。有意在构建路径触发的惰性加载必须有幂等状态保护，且检索/发现设置项不能执行控件副作用。

界面输入先更新绑定值、事件后提交派生状态；局部派生布尔值不能等到下次构建才写回，详见[UI 输入规则](ui-development.md)。

## 数据与兼容

新增持久化字段先确定旧文件缺失该字段时的行为。布尔功能默认开启时，不可随意使用 `omitempty` 导致用户关闭状态丢失；可以使用明确默认加载或有意的“隐藏”语义。

共享集合对读取者保持只读。后台工作拿复制快照，不持有可变切片、map 或视图。删除缓存必须限定受管理范围，不以字符串前缀判断路径归属，不覆盖用户已有导出文件。

涉及缓存键或版本时说明身份、账号 scope、音质、格式、有效期和迁移方案。不要借用清空用户数据来规避兼容性。

## 性能与可维护性

先复现、定位和测量，再优化。说明优化的是分配、CPU、GPU、I/O、首帧延迟还是空闲唤醒。不能用测试套件总耗时声称原生 GPU 性能提升。

长列表使用虚拟化；缓存有容量、失效和所有者；高频路径避免重复解码、全文扫描和不必要的重建。不要以性能为由绕过取消、资源释放、账号隔离或正确性测试。

无行为变化的整理尽量保持可审查，避免同时改 API、目录、格式和逻辑。版本、依赖、更新源、签名权限、安装脚本只随明确任务变更。

## 自审问题

提交前检查实际 diff，而非只看文件名：

- 变化能否对应到需求和验收条件？有无未被要求的行为？
- 是否增加第二份业务状态、反向导入或不必要包装？
- 失败、取消、重复操作、过期结果和资源释放是否完整？
- 是否保留旧配置、文件格式和平台行为？
- 测试是否真正会在回归时失败，而不是对实现细节或文案逐字断言？
- 新文件是否有多行简介、测试是否就近、文档链接是否更新？
- 是否存在调试开关、敏感数据、临时文件或未解释的测试删除？

具体完成检查参见[贡献指南](../CONTRIBUTING.md)与[测试手册](testing.md)。
