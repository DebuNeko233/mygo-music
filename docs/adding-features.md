# 按架构增加或修改功能

目的不是给每个功能造一套目录，而是让新行为有明确所有者和可验证边界。开始前阅读[架构](architecture.md)及对应[功能手册](features/README.md)；涉及 UI、异步或持久化时再读相应规则。

## 1. 写出可验收的行为

用操作描述需求：入口在哪里、用户做什么、成功后观察到什么、失败或取消怎样表现、重启是否保留。明确范围之外的行为，避免顺手增加另一套功能。

以侧栏开关为例：只允许隐藏每日推荐、最近播放、私人 FM、排行榜、播客、本地歌曲和音乐网盘；首页、搜索和资料库保持；立即生效并保存；隐藏不关闭当前页或改变播放。这些条件比“增加一个设置 bool”完整。

确认是否涉及真实账号写入、用户文件、依赖、版本、签名或外部发布。文档中的命令示例不替代任务授权。

## 2. 找现有路径

```sh
rg -n 'HiddenSidebarPages|sidebarSettings|func .*sidebar' internal
rg --files internal/ui/viewmodel internal/ui/view
rg -n '^func Test' internal/app/sidebar_settings_test.go
```

从实际入口追到命令、服务、状态发布和重绘。查看同类测试和平台实现。不要只按文件名选择 App，也不要为绕开旧代码复制播放器、缓存或 API 请求。

## 3. 先做所有权分配

| 新增内容 | 目标位置 |
| --- | --- |
| API 请求与响应解析 | `features/netease` |
| 无界面的算法或共享数据 | 对应底层服务/模型 |
| 功能加载、请求身份、重试、表单 | `ui/viewmodel/<feature>` |
| 控件、布局、焦点、动画 | `ui/view` 或功能视图子包 |
| 用户偏好字段和持久化 | `features/preferences` |
| 系统事件或跨功能操作 | App 适配文件与接线组 |
| 导航种类与历史规则 | `features/navigation` |
| 业务验证 | 最接近被验证所有者的测试包 |

复用已有包优先于建新包。若需要新包，说明它独立拥有的状态或依赖，检查是否会形成反向导入。只拆文件就能解决时不要增加层级。

## 4. 示例 A：持久化显示偏好

以现有侧栏功能为参照：

1. 在 [preferences.Settings](../internal/features/preferences/settings.go)中表达持久化值；旧文件缺字段时仍显示入口，因此使用 `HiddenSidebarPages` 的零值语义。
2. 在 [settings/sidebar.go](../internal/ui/view/settings/sidebar.go)中提供七项开关，显示文案属于视图。反向绑定在输入事件后提交，调用已有 Changed。
3. 在 [settings.go](../internal/ui/view/settings/settings.go)中注册可搜索设置分类，统一说明不在每行重复。
4. App [view.go](../internal/app/view.go)只传偏好值给 shell，不迁移路由或重建播放器。
5. [shell/sidebar.go](../internal/ui/view/shell/sidebar.go)过滤可选入口，保留固定入口与原有控件身份。
6. 用 [App 集成测试](../internal/app/sidebar_settings_test.go)验证点击、保存、重载、搜索及播放不变；shell 测试验证固定入口和恢复导航；preferences 测试验证旧文件兼容。

这个功能不需要新服务、goroutine、ViewModel 或轮询。若以后新增可隐藏项，必须先明确产品范围，再同步结构、UI、过滤、持久化兼容与功能文档，不能仅把页面枚举全部做成开关。

## 5. 示例 B：异步分页页面

以下是假设流程，不是待创建的真实功能目录：

### 数据与服务

先在协议层定义请求输入、响应和错误。服务接受取消上下文，返回普通数据，不引用 UI。明确分页游标取服务端原始条目还是可见条目；去重不能改变接口游标语义。

### 功能模型

定义数据、Loading、Error、分页状态及请求身份。命令区分首次加载、加载更多和刷新；重复操作是否合并需要明确。缓存旧内容、成功空结果和请求失败分别处理。

通过所需的 Fetch、Post、Valid 或小接口连接服务。Post 负责所属线程发布，模型检查请求身份。取消旧请求后仍拒绝已排队的旧回调；不要只比较资源 ID。

### 视图

定义 View 的数据和命令输入，以及独立 State 的滚动、句柄和动画。空、加载、错误、已有数据刷新中的状态都要可用。长列表复用虚拟行；更多加载入口有幂等保护。

### App 接线

在对应 `bindings_*.go` 中一次性注入，必要时加入导航与页面分发。跨账号有效性、全局错误提示、播放器和缓存作用域由 App 接入；不在模型里导入其他功能 ViewModel。

### 测试与文档

模型测试控制乱序返回、失败重试和分页重复；视图测试检查输入与状态；App 测试只覆盖账号、导航、播放等接线。添加功能手册并从索引进入，记录尚不支持的场景。

## 6. 常见变更的额外要求

| 变更 | 不可遗漏 |
| --- | --- |
| 新持久化字段 | 缺字段、旧文件、非法值、明确关闭状态、重载 |
| 新播放入口 | 起始歌曲、随机/循环语义、来源上报、当前队列是否保留 |
| 新缓存 | 身份、账号 scope、epoch、容量、失效、清理和退出 |
| 新导出格式 | 实际字节识别、标签读回、PCM 不变、定位、离线与签名运行 |
| 新原生窗口 | 创建/关闭所有者、隐藏/恢复、焦点、退出和平台回退 |
| 新后台任务 | 取消、去重、投递被拒绝、过期资源释放、关闭等待 |
| 新全局快捷键 | 配置冲突、注册失败、注销、重新注册后旧反馈 |
| 新字幕能力 | 模型可用性、取消/移除、时间覆盖、保存顺序、已有内容保持 |
| 删除功能 | 接线、状态、缓存/设置兼容、测试和文档引用 |

## 7. 从实现到交付

实现最小完整路径后先运行定向行为测试，再做架构、静态检查和全量回归。新增 UI 测试五次，异步共享状态跑相关 race，视觉变化实际看截图，原生变化补对应平台验证。规则与命令以[测试手册](testing.md)为准。

检查最终 diff：有没有顺手改版本或依赖、遗留旧包装、把测试移走但失去覆盖、引入第二份状态、忘记取消或释放、文档只描述计划而非实现。验证通过后按任务已有授权提交/推送；PR、CI 等待或发布只在要求范围内执行。

## 8. 审查者应能回答

- 用户从哪个入口触发，成功、失败与取消分别是什么结果？
- 每份新状态和资源由谁持有，跨账号/窗口/队列变化如何失效？
- 为什么放在这一层；是否增加无必要目录或通用抽象？
- 是否保留已有文件、设置和平台行为？
- 哪个测试会在这个行为回归时失败？是否有真实原生验证缺口？
- 哪份文档记录了最终契约，其他入口是否指向它？
