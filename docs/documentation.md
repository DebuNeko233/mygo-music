# 文档新增与维护规范

文档必须能指导当前代码的实现与审查。详细不等于复制源码或积累历史记录：保留决策、行为、边界和验证方法，删除已失效的说法。

## 1. 放在哪里

| 内容 | 位置 |
| --- | --- |
| 产品介绍、安装和基本使用 | 根 README |
| 如何参与、提交和交付 | 根 CONTRIBUTING.md 提供入口，详细流程维护在 docs/contributing.md，PR 模板仅提供填写结构 |
| 代码代理进入仓库的阅读入口 | 根 AGENTS.md |
| 技能触发与按任务加载文档 | `.agents/skills/<name>/SKILL.md` |
| 总体分层、依赖、状态职责 | docs/architecture.md |
| 跨功能开发规则 | docs 根目录已有主题手册 |
| 用户功能的实现契约 | docs/features/ 对应主题 |
| 正式发行操作 | 根 RELEASING.md |
| 已发布版本变化 | 根 CHANGELOG.md |
| 本次实现过程、测试日志、临时对比 | 提交/PR/任务记录或仓库外产物，不放长期 docs |

先查[总索引](README.md)和[功能索引](features/README.md)。已有主题可以清晰承载时更新原文，不为每个开关、文件或修复创建一份文档。一个新主题有独立所有者、流程和稳定读者时再拆文件；不设置机械字数门槛。

文件名用小写英文和连字符。中文用于正文与标题。根入口文件保留约定名称。不要再创建与 `.agents/` 重复的 `.agent/`；不要将另一套 DEVELOPMENT.md 与现有开发手册并行维护。

## 2. 新文档的必要内容

新功能文档按以下模板组织，可根据主题合并标题：

```markdown
# 功能名称

说明用户从哪里进入、能完成什么，以及不包含的相关能力。

## 代码与所有者

列服务、模型、视图、App 的实际路径；说明每份状态和资源归谁。

## 行为与流程

说明正常流程、命令语义和可观察结果。

## 失败、取消与兼容

写明空结果、失败、重试、请求过期、账号/窗口变化、旧数据和平台差异。

## 验证

链接已有回归，给必要的命令，说明原生或真实服务验证限制。

## 扩展注意事项

说明未来增加能力必须同步的代码、测试、配置及其他文档。
```

架构决策应说明问题、现状、选定边界、取舍和验证方式。未实现方案标记为提议，不能写进“当前行为”表。需要长期保存提案时先说明其用途，再决定目录；不要预先建立空的 ADR/设计文档层级。

## 3. 规则的写法

“必须”和“禁止”需要明确适用对象、原因及可执行检查；避免泛泛的“保证质量”。区分技术约束、团队约定、当前实现、示例和建议。

例如“ViewModel 不得导入 desktop，因为它必须可独立验证状态逻辑，架构测试检查此依赖”可执行；“任何改动都必须在三平台全套原生测试，否则不能动代码”会把无法满足的环境条件变成无意义阻断，应改为按变更范围验证并报告缺口。

工作流规则不能凭空扩大操作授权。读文档不等于允许真实账户写入、向他人发消息、提交 PR、发行或删除数据。用户已经明确授权的步骤也不能因默认模板再问一遍。

不要照抄个人开发机路径、账号、签名身份、历史 issue 号或一次会话的分支为所有人的前提。命令占位符要显式标识，示例输出不宣称实际运行结果。

## 4. 链接与引用

- 仓库内用相对 Markdown 链接，尽量指向实际文件或稳定目录，避免行号因日常修改失效。
- 同一条详细规则只维护一处，其他文档写短说明并链接。AGENTS 和 SKILL 不复制整个 UI/测试手册。
- 新主题从 docs/README.md 的任务入口或已链接的功能索引可到达；不能留下孤立文档。
- 移动或删除文件时全仓搜索旧路径，修复 README、CONTRIBUTING、AGENTS、技能和其他文档的引用。
- 引用外部 API 时优先固定版本的官方资料；仓库实现与通用文档不一致时明确本地差异。
- 不把调试产物、完整用户歌词、私有路径、凭据和用户数据库链接进公共文档。

## 5. 何时必须更新

以下变化应在同一交付中更新对应说明：层次/所有者变化，用户行为变化，新增设置与持久化格式，测试入口/环境开关变化，工具链/依赖替换，CI 或发行流程变化，新增/删除功能，以及文档路径变化。

单纯函数重命名若不改变文档中的路径或契约，不要求机械改文案。文档已错误时应修正并以实际源码为证据；不要为遵守旧文档保留错误实现。

## 6. 文档改动的校验

1. 阅读最终全文，确认目录与标题能回答读者的问题，没有把待做事项写成已实现能力。
2. 检查所有新增/修改的本地链接存在；锚点与目标标题一致。代码块中的路径与命令也要另行核对。
3. 全仓搜索被删除路径、旧术语和旧入口，检查是否仍有误导性导航。
4. 将架构、功能行为、配置默认值、依赖版本和 CI 声明与对应源码逐项对照。
5. 运行 `git diff --check`。若更新技能，同时运行本机可用的 skill 校验器并检查 YAML 元数据。
6. 文档里的命令若涉及真实操作，区分语法/入口核对和实际执行，不能为“验证文档”擅自推送、发布、删除用户数据或调用真实写接口。

纯文字与链接改动不需要新增测试，也不要求截图或竞态检查。若同时改代码、构建配置或可执行脚本，按[测试手册](testing.md)执行相应验证。已执行额外回归可以报告，但不能据此声称所有文档命令或平台都已验证。

目前仓库 CI 没有通用 Markdown 链接门禁。手工或临时脚本检查必须如实说明；若将来新增自动门禁，把脚本、工作流和本节一起更新，不预先声称存在。

## 7. 文档审查清单

审查者应能找到事实依据、代码所有者、失败路径、实际测试以及相关入口。删除一篇旧文档前，确认仍有效的特殊约束已融入新主题；不要保留两份内容相似但细节不同的指南作为“兼容”。

交付只说明最终组织、重要新增规则和实际校验结果，不把写作过程流水账当成果。后续发现文档与代码冲突，优先修复最靠近事实来源的页面，再检查所有引用入口。
