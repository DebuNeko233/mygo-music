# 依赖维护与上游同步

本项目保留上游音乐客户端的行为与更新能力，同时使用按功能划分的目录和明确的层次边界。同步上游是移植行为和修复，不能用上游旧目录覆盖本分支架构。

## 1. 当前基线与事实来源

| 项目 | 当前状态 | 核对来源 |
| --- | --- | --- |
| 应用上游 | `zhangnjsd/mygo-music` | Git remote、提交历史和 [mygo.json](../mygo.json) |
| 本分支维护仓库 | `DebuNeko233/mygo-music` | 实际 remote 和任务目标 |
| 已集成应用版本 | `0.2.16` | mygo.json、[CHANGELOG.md](../CHANGELOG.md)、合并历史 |
| MyGo require | `github.com/egoist/mygo v0.10.0` | [go.mod](../go.mod) |
| 实际 MyGo 实现 | `github.com/DebuNeko233/mygo v0.10.1-0.20261120193717-667973527550` | go.mod 的 replace |
| Go 工具链要求 | `go 1.27.4` | go.mod |

这些是写作时的仓库状态，不是“永远最新”的承诺。依赖变更时同步本表；执行操作始终重新读取实际配置。当前分支名也不是所有未来贡献的固定目标。

查看实际模块而非只读 require 行：

```sh
go list -m -json github.com/egoist/mygo
go list -m -f '{{.Dir}}' github.com/egoist/mygo
git remote -v
git log --oneline --decorate -12
```

本地 API 查证优先固定模块源码及其文档。涉及新版本能力时查对应版本的官方实现/变更记录；不能凭记忆使用尚未引入的 API。

## 2. 为什么保留 MyGo fork

当前 fork 保留歌词绘制层缓存能力（包括 `DrawCached`）和 macOS 帧就绪相关改动。应用已依赖这些能力与行为，因此把 replace 删除、让编译通过，不等于完成回归官方框架。

回归官方或更新 fork 需要逐项证明：

1. 应用使用的 API 在目标版本存在，或有语义相当的迁移实现。
2. 缓存层的失效、画布释放和字体/尺寸变化仍正确。
3. 原生绘制、动画、窗口事件与帧调度没有可观察退化。
4. macOS、Windows、Linux 的相关能力可构建，涉及的平台原生行为已实测或明确列出缺口。
5. 性能对照使用相同场景、硬件和采样方法，不能凭测试耗时宣布 GPU 性能提升。

禁止为跟随上游 go.mod 顺手删 replace，也不能为暂时通过测试删掉绘制缓存、降低特效质量或吞掉生命周期错误而不说明用户影响。需要替代方案时先实现并验证，再决定依赖切换。

## 3. 上游同步步骤

### 确认范围

确认工作区、当前 HEAD、目标远端分支、上游地址与要同步的版本/完整 SHA。先看已有改动，必要时建立隔离 worktree；不能 stash、reset 或覆盖别人的未提交工作。记录共同祖先，区分已移植的修复与新变化。

获取远端只更新引用，不等于授权推送其他分支或创建发行。网络不可用时报告无法确认最新状态，不用缓存引用冒充实时上游。

### 建立变更映射

先按行为分类，再决定落点：

| 上游改动形态 | 本架构落点 |
| --- | --- |
| App 内的页面绘制、组件与动画 | 对应 `desktop/view/<feature>` |
| App 内的搜索、分页、加载状态 | 对应 `viewmodel/<feature>` |
| 队列、解析、下载、文件和缓存算法 | 相应服务包 |
| 原生能力与框架适配 | desktop 能力包或已有平台适配包 |
| 登录隔离、全局导航和跨功能协调 | App |
| 混在 App 的单元/视图测试 | 按被测行为归属移动；真正接线测试留 App |

不要机械 cherry-pick 后把冲突全选 theirs/ours。没有文本冲突也可能有语义冲突：新调用绕过 ViewModel、新状态没有账号代次、新测试只检查旧 App 路径等。

### 实施与处理冲突

合并还是移植由实际历史决定；需要保留共同祖先关系时使用真实 merge。保留上游修复的行为、必要版权和提交说明，按现有架构调整实现及测试。

同时核对依赖、配置格式、资源、平台文件、生成器、CI 和发行源。版本变化应来自同步目标，不凭日期自行抬高版本。上游删除某字段前检查它在本地是否属于 ABI、持久化兼容或其他平台入口。

对每类冲突留下可审查的解释：上游解决什么问题、本地最终落点、保留哪些差异、通过哪个行为验证。解释放提交或交付记录；长期差异写在相关文档，不把完整冲突流水账塞进架构手册。

### 验证与交付

按[测试手册](testing.md)完成架构检查、构建、MyGo vet、全量测试及受影响 race。涉及框架、窗口、音频或签名的改动追加对应原生验证。检查新上游测试是否真的在本地路径运行，而不是变成未触发或跳过的测试。

交付说明上游完整 SHA、版本、主要行为变化、本地保留差异、验证范围。按已授权目标推送；用户要求直接推送就不额外创建 PR。不要将功能分支强推为上游 main。

## 4. 普通依赖更新

一次更新应有具体原因：功能所需、错误修复、安全修复或工具链要求。只更新相关模块，避免无关依赖大面积漂移；`go mod tidy` 的 diff 必须审查，不能因为命令成功就全部接受。

升级 MyGo 先核对新旧源码中的生命周期和 API；确有迁移需求时再使用该版本提供的迁移工具，先预览并人工检查结果。升级音频/标签依赖检查格式夹具、PCM、动态库、许可和签名运行时；升级 speech 检查生成绑定、模型版本及各平台原生资源。

新增第三方依赖说明它替代什么、为什么现有库不足、引入的运行时/体积/许可成本。不得仅为几行明确逻辑引入大型框架。

## 5. 发行配置的边界

目前应用更新源仍指向上游。开发 fork 并不意味着自动拥有上游的更新私钥或发行身份。独立发布需要明确授权，并确认更新源、密钥、版本策略、打包资源、签名和用户迁移；禁止复用个人凭据或静默把用户切到另一更新源。

正式发行操作在 [RELEASING.md](../RELEASING.md)，实际触发条件在 [.github/workflows/release.yml](../.github/workflows/release.yml)。普通依赖更新不创建 tag、不发布 release，也不修改更新签名策略。
